# Security Phase 2 — Database and Delivery Design (Proposal)

Status: design only. This document does not change the database, production services, secrets, DNS, or deployment configuration.

## Goals

1. Make inbound and outbound idempotency safe under concurrent requests.
2. Enforce rate limits atomically across concurrent API and webhook workers.
3. Persist inbound automation and outbound delivery work before acknowledging or attempting asynchronous processing.
4. Preserve agent ownership boundaries and auditable operator controls.

## 1. Idempotency model

### Current schema observations

The initial schema defines `messages.idempotency_key TEXT UNIQUE`. That is a single global uniqueness scope shared by inbound and outbound messages. The application now scopes duplicate reads by direction, but the global constraint can still create cross-direction collisions. The current application also performs read-then-insert duplicate checks, which are race-prone without a database uniqueness guarantee.

### Proposed constraints

Use partial unique indexes, after auditing and resolving existing duplicate data:

- Inbound delivery key: unique on `messages(idempotency_key)` where `direction = 'inbound' AND idempotency_key IS NOT NULL`.
- Outbound request key: unique on `messages(sender_id, idempotency_key)` where `direction = 'outbound' AND idempotency_key IS NOT NULL`.
- Inbound provider ID: unique on `messages(provider_message_id)` where `direction = 'inbound' AND provider_message_id IS NOT NULL`.
- Consider provider-scoped uniqueness if multiple channel providers can write the same table; the current schema has no provider/channel column on messages, so add an explicit provider identity before relying on cross-provider uniqueness.

Before adding constraints, run duplicate-detection queries and produce a reviewed cleanup report. Do not silently delete or rewrite message history.

### Application behavior

- Replace read-then-insert as the correctness boundary with insert-on-conflict / database-returned existing row semantics.
- Keep authorization checks before returning an existing outbound message.
- Scope outbound idempotency to the authenticated sender (or tenant + sender if tenancy is introduced).
- On conflict, fetch the canonical row under the same ownership scope; do not send to the provider again.
- Treat database errors as fail-closed.
- Idempotency keys must be stable across retries and generated by the trusted caller or server, never derived from message body alone.

## 2. Atomic rate limiting

Current read/count/check logic is not atomic: concurrent requests can all observe capacity and exceed a configured limit.

### Proposed database primitive

Create a PostgreSQL RPC that accepts a bounded set of rate-limit dimensions and atomically increments counters using a transaction and unique bucket keys. Dimensions should cover:

- global hourly and daily;
- agent hourly and daily;
- contact hourly and daily.

Use a bucket table keyed by `(scope_type, scope_id, window_kind, window_start)`, with a non-negative counter and database-generated timestamps. The RPC must:

1. Validate scope types and positive limits.
2. Derive window boundaries using database time (UTC).
3. Increment with `INSERT ... ON CONFLICT DO UPDATE ... WHERE count < limit`.
4. Return an explicit allowed/denied result and remaining capacity.
5. Perform all applicable dimensions in one transaction so a denial does not consume capacity in the other dimensions.
6. Fail closed on database/RPC errors.

Do not rely on client clocks. Add bounded retention cleanup for expired buckets. Decide whether a denied attempt should be counted separately in an abuse/audit table rather than incrementing successful-send counters.

### Emergency stop

Keep the persisted pause state as an independent hard gate. Check it immediately before enqueue/dispatch, and again in the worker immediately before provider submission. A paused system must not dispatch already queued work until resumed.

## 3. Durable queue / transactional outbox

### Proposed tables

A dedicated `message_outbox` (or `delivery_jobs`) table should store:

- UUID primary key;
- message UUID foreign key;
- direction and event type;
- status: `pending | processing | retry | delivered | dead_letter | outcome_unknown`;
- attempt count, next-attempt timestamp;
- lease owner and lease expiry;
- last safe error code (no secrets or raw provider payload);
- provider message ID and delivered timestamp;
- created/updated timestamps.

Add a unique key linking one logical delivery event to one message. Do not duplicate message content in the outbox unless there is a documented need; reference the canonical message row.

### Transaction boundaries

- Inbound webhook: insert inbound message and its automation outbox event in one database transaction/RPC. Acknowledge the provider only after this transaction commits.
- Outbound API: create the queued message and its outbox event in one transaction/RPC. Return an accepted/queued response; a worker performs provider I/O.
- Workers claim jobs using `FOR UPDATE SKIP LOCKED` with a short lease, increment attempts, and commit the claim before network I/O.
- Never hold a database transaction open during provider network calls.
- On confirmed provider acceptance, persist provider ID and mark delivered.
- On explicit provider rejection, retry only if classified as transient; permanent rejection goes to dead letter.
- On timeout/connection loss with unknown provider outcome, set `outcome_unknown`. Do not blindly retry unless the provider supports a stable idempotency key or a status lookup that can reconcile acceptance.
- Worker lease expiry enables recovery after crashes; attempt caps and exponential backoff with jitter prevent retry storms.

### Delivery semantics

The system can provide durable at-least-once processing, not universal exactly-once delivery. Exactly-once external delivery is only achievable when the provider supports idempotent submission or reliable reconciliation. Document this limitation in the API contract and operator dashboard.

## 4. Inbound workflow

1. Verify webhook signature over exact raw bytes.
2. Parse and validate the batch with strict size/event bounds.
3. In one database transaction per event (or whole batch, after deciding batch-size limits), upsert contact/conversation safely, insert the inbound message under unique idempotency constraints, and enqueue automation.
4. Acknowledge only after commit.
5. Worker performs opt-out, complaint classification, routing, AI response generation, and any outbound enqueue as separately observable steps.
6. Persist processing state and bounded retry metadata. Ensure opt-out suppresses pending marketing replies before dispatch.

Do not perform AI generation or provider sends inline in the webhook request.

## 5. Agent isolation and tenant boundaries

- Keep ownership decisions server-side; never accept `assigned_agent`, tenant ID, or sender identity as trusted client fields.
- Every worker job must carry a canonical resource ID and resolve current ownership from the database at execution time.
- Re-check contact consent/opt-out, conversation assignment, emergency stop, and agent permissions immediately before outbound dispatch.
- Admin access must be explicit and audited.
- If multi-tenant support is introduced, include tenant ID in every unique key, queue claim, rate-limit dimension, and ownership query.

## 6. Required migration and rollout gates

No migration is included or applied by this proposal. Before implementation:

1. Inspect the actual live schema and migration history; the checked-in initial migration is not proof of production schema.
2. Audit duplicate idempotency keys, duplicate inbound provider IDs, orphan messages, and existing status distributions.
3. Confirm provider capabilities: stable idempotency key, message status lookup, webhook retry policy, and delivery receipts.
4. Design backward-compatible migrations and RPC permissions; service-role-only execution for internal RPCs.
5. Add integration tests against real PostgreSQL semantics, including concurrent duplicate inserts and concurrent limit consumption.
6. Roll out schema first, then application code with feature flags; verify metrics before enabling workers.
7. Keep rollback steps and a reconciliation runbook for queued and outcome-unknown messages.

## 7. Acceptance tests

- Two simultaneous inbound deliveries with the same delivery key create one canonical inbound message and one automation job.
- Two simultaneous inbound deliveries with the same provider message ID create one canonical inbound message.
- Same idempotency key used by inbound and outbound traffic does not cross-collide.
- Same outbound key from different agents is isolated; repeated key from the same agent returns the canonical message without a second provider send.
- Concurrent requests at the rate-limit boundary never exceed configured limits.
- A multi-dimension rate-limit denial consumes no successful-send capacity in any dimension.
- Database/RPC failure blocks dispatch.
- Webhook returns success only after durable message + outbox commit.
- Worker crash after claim is recovered after lease expiry.
- Provider timeout transitions to `outcome_unknown` and is not blindly retried.
- Opt-out and emergency stop are rechecked immediately before provider submission.
- An agent cannot process another agent's message by altering job IDs or request payloads.
